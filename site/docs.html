Every eds command, A to Z. The CLI is a dev tool - it ships nothing to your site. Run any command from inside your EDS project (anywhere with a fstab.yaml); it finds the project root automatically. Run eds on its own for an interactive menu.

Install

Node.js 20 or newer. Installs the eds command globally.

$ npm i -g aem-eds-kit

From zero to a page - pick your authoring model

It's a big tool, so here's the exact command path for each authoring model, start to published page. Steps 1 and 3-5 are shared; the content step (6) differs. Every step is interactive when you omit the flags.

DAda.live
  1. 1npm i -g aem-eds-kit
  2. 2eds init --authoring da --org … --site …
  3. 3eds scaffold ue · eds scaffold helpers
  4. 4eds block from-design (or create / migrate)
  5. 5eds model add · schema block · track block
  6. 6eds template new home --blocks … --push → pushed to DA
  7. 7eds preview /… → eds publish /…

  1. 1npm i -g aem-eds-kit
  2. 2eds init --authoring gdrive --mountpoint <drive-folder>
  3. 3eds scaffold ue · eds scaffold helpers

  6. 6eds template new home → import templates/home.html into a Google Doc; share the folder + install aem-code-sync
  7. 7eds preview /… → eds publish /…

  3. 3eds scaffold ue · eds scaffold helpers

eds (interactive menu)

Run with no arguments to open an interactive menu that routes to every feature's own wizard: set up the project, generate a block from a design, migrate a classic AEM component, scaffold, create a block, add an integration, preview, Admin API, audits, Figma setup. In CI / piped shells it prints help instead.

$ eds

eds init

Adapt a freshly cloned EDS boilerplate to your setup in one interactive wizard. Pick the authoring model - Universal Editor (crosswalk), DA (da.live), Google Drive or SharePoint - and eds sets the project name (package.json + boilerplate placeholders), writes fstab.yaml only when the model needs it (UE/crosswalk doesn't), scaffolds the crosswalk config + paths.json for UE, optionally adds the CI workflow, then walks the external steps (AEM Code Sync app, content share, Sidekick) as a clickable checklist.

$ eds init
# or non-interactive:
$ eds init --name my-site --authoring da --org my-org --site my-site --yes
--name <name>Project name (kebab-case)
--authoring <model>ue | da | gdrive | sharepoint
--mountpoint <url>Content source URL (document models)
--org / --siteDA org / site (--authoring da)
--no-ciSkip the GitHub Actions workflow
--yesSkip prompts; apply with flags/defaults

eds template new <name>

Generate EDS page initial content - the EDS analog of an AEM template: a document of sections + chosen blocks + a metadata block. Always writes templates/<name>.html, then routes by your authoring model (detected from fstab.yaml / markers, or --authoring): DA → push to da.live; Google Docs / SharePoint → importable doc + external steps; Universal Editor → registers the seeded blocks in component-filters.json and points to the AEM editable template.

$ eds template new homepage
$ eds template new homepage --blocks hero,cards --push --org my-org --site my-site
--blocks <list>Comma-separated block ids to seed
--title / --description / --areaPage title, description, metadata label
--path <path>Content path (default /templates/<name>)
--authoring <model>Force da | gdrive | sharepoint | ue (else detected)
--pushPush to DA (da.live)
--org / --siteDA org / site (else from .edsrc.json)

eds block from-design [design-url]

Turn a design - Figma, Google Stitch, Canva, Sketch or Framer - into an EDS block. Run with no URL for a step-by-step wizard whose first step picks the design source (it's a wizard choice, not a flag), then name, link, content source, UE model, screenshot and run mode. The CLI builds a prompt with your project tokens + EDS conventions and hands it to your AI agent (Claude Code / Cursor / Codex), which reads the design through that source's MCP connection and writes the block - JS, CSS and a Universal Editor model - then self-verifies. You see a live, colour-coded log with per-phase timings. On success it auto-starts the live preview.

Figma is the most battle-tested source and stays pixel-perfect (get_design_context / get_variable_defs / get_screenshot); the others read the design through their own MCP. A Figma link is parsed into its file key + node id; other sources take the link as-is, so pass --name with them.

$ eds block from-design
# or non-interactive:
$ eds block from-design "https://figma.com/design/KEY/Name?node-id=42-100" --name hero
--name <name>Block name (otherwise inferred from the file)
--source <type>Content source: document | ue | cf | mixed
--agent <type>Force agent: claude | cursor | codex | none
--dry-runBuild the prompt only; don't run an agent
--no-ue-modelSkip the Universal Editor model
--no-screenshotSkip the screenshot (fewer tokens; structural verification)
--no-serveDon't auto-start the live preview
--yesSkip confirmation prompts

eds block create <name>

Scaffold an empty block - <name>.js, <name>.css, and a Universal Editor model _<name>.json (title + heading-level select + rich text) by default, so it's authorable in UE immediately.

$ eds block create hero-banner
$ eds block create hero-banner --no-ue-model

eds block list

List every block with its file status, UE model and Figma source. --json for tooling.

$ eds block list
$ eds block list --json

eds block preview <name>

Serve a live, breakpoint-switchable preview in your browser - nothing is written to your project (the harness is served from memory). A dropdown switches the block between widths inside an iframe, so its media queries fire against the chosen width. Edits to the block live-reload the browser. Breakpoints and an "Open in Figma" link come from the block's .eds-meta.json.

$ eds block preview hero
$ eds block preview hero --widths 375,768,1280 --port 9000 --no-open
--port <port>Port to serve on (default 8777, falls back if taken)
--widths <list>Comma-separated breakpoint widths
--no-openDon't open the browser automatically

eds track block <name>

Instrument a block's decorate() with dataLayer tracking on demand: a delegated block_click (links/buttons, label from data-track or the element text) and form_submit, pushed through trackEvent from scripts/analytics.js (created by eds integrate gtm). Adds the import, injects at the top of decorate, idempotent, keeps the real parameter name. Also offered after block from-design and migrate component.

$ eds track block hero
$ eds track block hero --no-submit
--no-clickSkip click tracking
--no-submitSkip form-submit tracking

eds schema block <name>

Inject a JSON-LD (schema.org) structured-data builder into a block's decorate() for SEO / rich results. Pick a type - Article, FAQPage, BreadcrumbList, Product, Organization, LocalBusiness, Event, VideoObject, Recipe, HowTo - and it appends a <script type="application/ld+json"> to the head, built from the block's content (aliased to root). Idempotent; some fields are heuristic or TODO, so review and validate with Google's Rich Results test.

$ eds schema block faq --type FAQPage
$ eds schema block article      # interactive picker
--type <type>schema.org type (Article, FAQPage, Product, ...)
--yesSkip prompts

eds model add <block> [partials...]

Compose reusable field groups (partials) into a block's Universal Editor model (_<block>.json) instead of hand-writing fields. Fields are added by name, so re-running never duplicates. Partials are built from typed field helpers (each sets the right valueType), and the same catalog is referenced in the from-design / migrate prompt so the agent reuses the standard groups. Built-in: heading, eyebrow, image, richtext, link, cta, cta-group, classes, embed, teaser, card.

$ eds model add hero teaser
$ eds model add cards card cta-group
$ eds model add hero            # interactive picker

eds migrate component [dir]

Start migrating a classic AEM component to EDS. Phase 1 is deterministic (no agent, no network): it parses the Touch UI dialog (_cq_dialog/.content.xml) and maps its Granite/Coral fields onto the 17 Universal Editor field types - selects keep their options, multifields become repeatable containers, tabs are preserved - then writes blocks/<name>/ with a UE model, a decorate() stub, and a scoped CSS file to fill from the component's clientlib or rendered page.

$ eds migrate component ./components/hero
$ eds migrate component ./components/hero --name hero --yes
--name <name>Block name (otherwise inferred from the component)
--clientlib <dir>Path to the component's clientlib (otherwise auto-detected)
--yesSkip confirmation prompts

It also pulls the component's clientlib CSS into the block (honours css.txt + #base=, flags LESS/SCSS). A starting point to review and scope under .<block>; the faithful rendered-CSS capture comes in a later phase.

eds scaffold ue

Write (and merge into) the three UE config files - component-definition.json, component-models.json, component-filters.json - with the default-content components (text, image, button, title) and a field-reference block whose model demonstrates all 17 UE field types plus a multifield. Merge-by-id, so it never clobbers your config.

$ eds scaffold ue

eds scaffold blocks [names...]

Scaffold standard Block Collection blocks - hero, cards, columns, accordion, embed - each with JS/CSS and a distributed _<name>.json UE model (cards & accordion use the container/child-item multifield pattern), registered in the section filter. No names = all. Existing blocks are skipped.

$ eds scaffold blocks
$ eds scaffold blocks hero cards

eds scaffold ci

Generate a GitHub Actions workflow (.github/workflows/eds.yml) that gatekeeps every PR and push to main: it installs deps, runs the project's own lint/build if defined, then the eds audits - doctor, audit loading, audit security - which exit non-zero on problems. Deterministic, no agent. Won't overwrite an existing workflow.

$ eds scaffold ci

eds scaffold helpers

Write scripts/utils.js - tick the helpers you want in an interactive checkbox (dependencies pulled in automatically), or pass names. Available: toCamelCase, getPagePath / getLanguageRootPath, getSiteArea (top-level area like blog), getEnvironment, getContentTopic, isUEEdit / isUEPreview / isUE, and getMetadata. Self-contained; won't overwrite an existing file.

$ eds scaffold helpers

eds integrate [type]

Add a third-party service to scripts/delayed.js - the EDS-correct place for non-critical code (delayed phase, after LCP, zero Core Web Vitals impact). Chat widgets use the facade pattern (load on first interaction).

$ eds integrate            # interactive
$ eds integrate gtm
gtmGoogle Tag Manager
ga4Google Analytics 4
chatChat widget (facade)
cookiebotCookie consent (Cookiebot)
customAny script URL

eds figma setup

Interactive wizard: detect installed AI agents, check whether Figma MCP is configured, show the install commands if not, and save your preference to ~/.eds/config.json.

$ eds figma setup

eds doctor

Audit the project for common issues: fstab.yaml valid, head.html present, every block has a .js and a UE model, no console.log, Figma-sync freshness, config present. --json supported.

$ eds doctor

eds audit loading

Audit the three-phase loading strategy and LCP budget: nothing render-blocking in head.html, eager phase loads only the first section, styles.css within budget, no heavy libraries in blocks, block CSS scoped.

$ eds audit loading

eds audit security

Scan for vulnerabilities (npm audit) and exploit patterns: eval, dynamic innerHTML, document.write, javascript: URLs, hardcoded secrets / keys, mixed content, target="_blank" tabnabbing, postMessage('*'). Exits non-zero on critical/high - wire it into CI.

$ eds audit security
$ eds audit security --json

eds preview / publish [paths...]

Preview (staging) or publish (go live) pages through the AEM Admin API. Run with no paths for an interactive wizard (operation, org/site/ref, paths, confirmation). org, site and ref default from .edsrc.json.

$ eds preview               # wizard
$ eds preview /index /about
$ eds publish /index --org my-org --site my-repo --ref main

--quietErrors only

Content sources

Blocks can be driven by different content models - pick one in the from-design wizard or with --source:

documentDefault EDS - decorate() enhances the authored DOM
ueUniversal Editor authoring
cfContent Fragment - async decorate() fetches a CF via GraphQL
mixedSome fields authored inline (UE) + some from a Content Fragment, in one block

The source and the UE model go together: pick ue, cf or mixed and the Universal Editor model is generated so authors can edit in context. With document (Google-Docs-style authoring) a UE model isn't used - add --no-ue-model if you don't want one.

Universal Editor field types

Generated UE models use the full catalog of all 17 field component types: text, textarea, richtext, reference, aem-content, aem-content-fragment, aem-experience-fragment, aem-tag, select, multiselect, checkbox-group, radio-group, boolean, number, date-time, container (multifield), tab. Run eds scaffold ue for a live reference in your own project.
