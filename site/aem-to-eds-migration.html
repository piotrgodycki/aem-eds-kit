aem-eds-kit / AEM to EDS migration

AEM to EDS Migration Guide

Migrating from classic Adobe Experience Manager (AEM Sites) to Edge Delivery Services (EDS) means two separate jobs: moving components (dialogs, HTL, CSS) and moving content (authored pages). aem-eds-kit automates the component side deterministically and scaffolds the rest, so you don't rebuild everything by hand or burn tokens doing it.

The two migrations

Keep them separate - they have different best sources:

WhatBest sourceHow
Component + dialogrepo XML (_cq_dialog/.content.xml)eds migrate component - deterministic, no agent
Component CSSclientlib on disk / rendered pagepulled into the block CSS, scoped
Component HTML/JSHTL + rendered DOMported to decorate() (agent-assisted)
Authored contentrendered HTML of live pagesimport / scrape, then author in your content source

Why dialogs map cleanly

A classic AEM component stores its authoring schema in a Touch UI dialog. Granite/Coral has a finite set of sling:resourceType field types, so mapping them onto the 17 Universal Editor field types is a deterministic table - not guesswork:

Migrate a component, step by step

  1. Install the CLI: npm i -g aem-eds-kit
  2. Set up the target EDS project (pick your authoring model): eds init
  3. Migrate the component's dialog into a block + Universal Editor model: 
    $ eds migrate component ./ui.apps/.../components/hero
    This parses the dialog, maps the fields, and writes blocks/hero/ with hero.js, hero.css and the UE model _hero.json - pulling the component's clientlib CSS in automatically.
  4. Port the HTL behaviour into decorate() and review the scoped CSS.
  5. Enrich if needed: eds model add hero teaser, eds schema block hero --type Article, eds track block hero.
  6. Preview the block width-honestly: eds block preview hero.

Getting the CSS right

The authored clientlib CSS (often LESS) is a starting point; the most faithful CSS comes from the rendered page, because it resolves variables and the cascade. Bring the component's real styles into the block CSS and scope them under .hero.

Migrating content

Authored pages are best migrated from their rendered HTML, not from JCR XML or Sling Model JSON (which carry data, not the full visual structure). Scrape the live page, map its sections to EDS blocks, and author the result in your content source. Where to put it depends on the model:

  • Document Authoring (Google Drive, SharePoint, DA/da.live) - starter documents / initial content. Generate a page with eds template new; for DA it pushes straight to da.live.
  • Universal Editor (crosswalk) - author in AEM via the Universal Editor; the repo holds the component library (component-definition / -models / -filters).

Not sure which model fits? eds init walks you through Universal Editor, DA, Google Drive and SharePoint and configures the repo accordingly.

FAQ

Is AEM to EDS migration automatic?

The deterministic parts are: dialog to Universal Editor model mapping and clientlib CSS extraction run with no agent and no tokens. HTL to vanilla JS and final styling are agent-assisted or manual, because they involve behaviour, not just a schema.

Do I need to rewrite every component?

No. eds migrate component generates the block skeleton + authoring model for each component from its dialog, so you start from a working structure instead of a blank file.

Does EDS use templates like AEM /conf?

Not a single /conf. For document models, templates are starter documents (initial content); for Universal Editor, they're AEM editable templates plus the component library. eds template new generates the initial content either way.
